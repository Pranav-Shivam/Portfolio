Stage 01 — Flagship

LLM-Based RFQ Extraction & Processing System

The system I'd walk through in a system-design interview. Turns unstructured RFQ emails across 72 inboxes into validated, quote-ready data — with the retry logic, caching, and human-review fallback that make it trustworthy in production, not just a demo.

Email (72 inboxes)→ Graph API ingestion→ ETL → Snowflake→ PDF extraction→ Chunking→ LLM extraction→ Dedupe + Spec agents→ Structured output

Problem

An enterprise construction-materials distributor received RFQs as unstructured email attachments — PDFs, scanned specs, spreadsheets — across 72 regional inboxes. Estimators manually read each document, extracted material specs, cross-checked for duplicate quote codes, and re-keyed data into the quoting system. At baseline, only ~10% of RFQs cleared without manual intervention; the rest cost an estimator 15–30 minutes each, and manual re-keying errors propagated straight into customer-facing quotes.

Solution

Built an ingestion-to-structured-output pipeline that needs no human touch for the majority of RFQs. Three production agents run it: a Snowflake Sync Agent normalizing intake across all 72 inboxes, a Dedupe Agent using multi-algorithm scoring to flag duplicate quote codes before they reach an estimator, and a Material Specification Agent extracting and validating spec data against the product catalog. A fourth, the Missing Info Agent, proactively emails the customer when required fields are absent instead of leaving the RFQ stuck in a queue. Automation rate: 10% → 85%.

Challenges

  • Ingestion at scale. 72 inboxes on Graph API guarantees rate limits and dropped webhooks. Handled with delta-query polling as a fallback, exponential backoff on 429s, and idempotent writes keyed on message ID — a redelivered webhook can't create a duplicate record.
  • Inconsistent PDF quality. Scanned documents and specs embedded in free text break naive extraction. Layout-aware parsing plus a per-field confidence score; anything below threshold routes to human review instead of shipping a wrong spec into a quote.
  • Cost and latency at inbox scale. Full extraction on every attachment across 72 inboxes gets expensive fast. A caching layer (~65% hit rate — many RFQs reuse near-identical spec templates from repeat customers) plus two-tier model routing (cheap pass for classification/dedupe pre-filter, full model only when needed) cut end-to-end latency ~65%.
  • Duplicate detection isn't one rule. Quote codes resurface with formatting differences, revision numbers, or via different inboxes. Multi-algorithm scoring, not a single string match, cut manual cross-check workload 20–30%.

Decisions & Trade-offs

  • Human-in-the-loop over full automation. A wrong material spec in a customer quote is expensive to unwind. Traded a few points of automation rate for correctness — 85% automated, 15% to review, instead of forcing 100%.
  • Caching over always-fresh extraction. Re-running LLM extraction on every RFQ regardless of similarity is simpler but slower and costlier. Cached against a similarity threshold, accepting cache-invalidation complexity for the latency/cost win.
  • Splitting OLTP/OLAP, not patching around it. One Snowflake workload was the right call to ship fast early. As multi-org expansion increases write volume, that coupling now bottlenecks — currently decoupling rather than working around it.
  • Designing multi-tenancy for ~1,500 users, not the current 250. The single-org identity model doesn't hold under multi-org expansion. Evaluating shared-schema-with-isolation vs. siloed-per-org before committing, since the wrong call is expensive to reverse once more orgs are onboarded.

Scaling: 250 → ~1,500 users

  • Where it breaks first. At current volume (~3,000+ RFQs/month across 72 inboxes, estimated), the shared OLTP/OLAP Snowflake workload and a fixed connection pool are the first ceiling — projected to saturate well before 1,500 users if write-heavy dedupe queries keep competing with estimator read traffic on the same warehouse.
  • Fix in progress, not a rewrite. Decoupling OLTP (transactional writes from ingestion) from OLAP (estimator dashboards, reporting) onto separate warehouses, so a burst of inbound RFQs can't stall someone pulling a report.
  • Identity at 6x the orgs. Single-org Entra ID setup doesn't hold under multi-org expansion — evaluating shared-schema-with-tenant-isolation vs. siloed-per-org before onboarding the next cohort, since migrating tenancy model after data lands is far more expensive than before.
  • Capacity math, not guesswork. Peak inbound is bursty (Monday-morning RFQ floods across 72 inboxes) rather than flat — sizing the ingestion queue and LLM-call concurrency limits off p95 burst volume, not average daily volume.

Failure Handling

  • Transient API failures. Graph API 429s and 5xxs: exponential backoff, capped at 3 retries, then the message drops to a dead-letter queue for manual replay instead of silently dropping the RFQ.
  • Partial extraction. A multi-line-item RFQ where 8 of 10 line items extract cleanly doesn't get discarded or force-completed — the record ships with the 8 confirmed fields and the 2 low-confidence ones flagged for review, rather than blocking the whole RFQ on the worst field.
  • Bad or corrupted PDFs. Password-protected, scanned-at-an-angle, or malformed attachments fail layout-aware parsing outright. These are quarantined with the original message ID (not deleted) and surfaced to the review queue with a "parse failed" reason, so nothing silently vanishes.
  • LLM output that doesn't fit the schema. Function-calling output is validated against the expected schema before it's trusted; a malformed or hallucinated field triggers one retry with a stricter, more constrained prompt before falling back to human review — never shipped un-validated.

Parametric Estimation Platform

UAT · going live
15–16 legacy tools→ Formula extraction→ Versioned Rule Catalog→ 14-stage calc engine→ Takeoff generation→ Quote

Problem

Glazing/facade estimators worked across 15–16 fragmented legacy tools — spreadsheets and standalone calculators, each covering a different stage. 150+ business formulas existed only in institutional memory and manual worksheets, not code. There was no single source of truth: the same window system priced differently depending on which estimator and which tool touched it, across a 14-stage flow with 300+ variables, with no way to trace which formula version priced a given quote.

Solution

Replaced all 15–16 legacy tools with one calculation engine. Digitized the 150+ formulas into a versioned, auditable Rule Catalog that customers edit directly — no engineering ticket required to change a formula. Deliberately rules-based, not LLM-driven: pricing math is a known, finite decision space where determinism and auditability matter more than flexibility. The full 14-stage pipeline runs against 300+ variables per project, with every calculation traceable to the exact formula version that produced it.

Challenges

  • Extracting formulas from inconsistent legacy tools. Different tools used different rounding conventions and unit systems for the same calculation. Built a shadow-mode validation harness that ran the new engine against the same historical projects as every legacy tool before any customer cutover, instead of spot-checking.
  • Live-editable formulas vs. issued quotes. A customer changing a formula mid-cycle can't retroactively alter a quote already sent to their customer. Solved with immutable formula-version snapshots pinned to each quote at creation time.
  • 300+ variables per calculation. Naive re-evaluation of all 14 stages per change was slow. Precomputed shared intermediate values across stages to cut redundant calculation.

Trade-offs

  • Rules-based over LLM. Deterministic and auditable at near-zero marginal cost per calculation, versus an LLM's non-determinism and missing audit trail — wrong fit for pricing math, right fit here.
  • Customer-editable Rule Catalog over engineering-gated changes. Larger support/QA surface, but removes the estimation team as a bottleneck on every formula tweak.
  • Shadow-mode cutover over big-bang replacement. Slower rollout, but zero pricing-error incidents at go-live — validated against legacy-tool output first, not after.

AI Document Intelligence Platform

2 variants shipped
Document ingest→ Chunking→ Embedding (Qdrant)→ Relationship graph→ Hybrid retrieval→ Tenant-scoped chatbot

Problem

Enterprise clients needed Q&A over large internal document corpora — specs, contracts, manuals — without one tenant's documents ever surfacing to another. Flat vector search alone missed multi-hop questions ("which vendor spec supersedes which addendum") that need relationship context between documents, not just similarity.

Solution

Shipped two variants — a client-specific deployment and a generalized multi-tenant platform — both backed by semantic search over Qdrant plus a Graph-RAG layer that captures document relationships (supersedes, references, amends) alongside embeddings. Retrieval is hybrid: vector similarity plus graph traversal, feeding an LLM chatbot grounded on the retrieved context. The multi-tenant backend enforces isolation at query time, not as a post-hoc filter.

Challenges

  • Multi-hop questions plain vector search misses. Answers needing 2–3 document hops (spec → addendum → contract) don't surface from similarity alone. Layered graph traversal on top of vector retrieval instead of relying on either alone.
  • Tenant isolation under shared infrastructure. Query-time tenant scoping is enforced before retrieval runs, not filtered from results afterward — a scoping bug can't leak cross-tenant chunks by construction.
  • Generalizing without a rewrite. Kept the tenant boundary explicit in the data model from the first, client-specific build, so going multi-tenant later was a scaling exercise, not a redesign.

Trade-offs

  • Graph-RAG over flat RAG. Added retrieval latency and graph-maintenance cost, but flat vector search was measurably missing multi-hop answers in evaluation — worth the overhead.
  • Client-specific first, generalize second. Shipped narrow scope to one client fast rather than building multi-tenancy speculatively before a second tenant existed to validate it against.

Stage 03 — Design

How I design scalable AI systems

The principles and trade-offs behind every system above — not abstract theory, the actual calls made in production.

Principles

  • Correctness over automation rate. A system that's wrong silently is worse than one that's honest about its confidence. Every pipeline gets a confidence threshold and a human-review path for the tail — 100% automation is a red flag in domains where errors are costly.
  • Cost is an architecture decision, not a post-launch fix. Model routing (cheap model for filtering, capable model only where needed) and similarity-based caching are designed in from the start, not bolted on after the first bill.
  • Idempotency at every ingestion boundary. Anything pulling from an external system will redeliver, retry, or duplicate. Every write is keyed so a replay can't corrupt state.
  • Multi-tenancy is a day-one decision. Retrofitting tenant isolation after the fact is one of the most expensive mistakes to unwind — decided explicitly, even when the first customer is the only customer.

Trade-offs I weigh explicitly

  • Batch vs. real-time. Real-time isn't always worth the complexity — used where estimators are blocked waiting, batched where staleness costs nothing.
  • LLM vs. rules-based logic. LLMs for open-ended extraction over unstructured input. Deterministic rules for anything with a known, finite decision space — cheaper, faster, auditable.
  • Single-tenant simplicity vs. multi-tenant complexity. Ship single-tenant first when there's one customer, but keep the tenant boundary explicit in the data model so the later migration is a scaling exercise, not a rewrite.
